# Encore v1.8.0 — Mailgun Delivery Feedback

- Status: Implemented locally; webhook and invitation issuing remain disabled
- Date: 6 September 2026
- Scope: Invitation delivery evidence, complaint suppression and organiser visibility

## Release Notes

Encore can receive signed Mailgun delivered, failed and complained events and
correlate them to its own invitation delivery UUID. Organisers see privacy-safe
delivery totals on each independently managed performance. Recipient addresses
and Mailgun's free-text diagnostic payload are not retained in webhook evidence
or audits.

Permanent failures mark the protected contact undeliverable. Complaints suppress
the contact and revoke the affected unused invitation. Temporary failures remain
distinct so a later successful delivery can supersede them.

## Architecture Changes

The existing invitation/delivery separation remains authoritative. A new
`mailgun_delivery_events` receipt records minimal provider evidence and makes
event and signature-token replay idempotent. Mailgun receives only the Encore
delivery UUID as message metadata; it does not become an owner of reviewer,
attendance or reputation state.

## Operational Changes

The web runtime gains an independently gated signed webhook endpoint at
`/api/webhooks/mailgun`. It requires Mailgun's HTTP webhook signing key and a
bounded timestamp tolerance. Invitation issuing and webhook ingestion remain
separate controls.

## Breaking Changes

The internal `ReviewInvitationSender` interface now accepts the delivery UUID so
the mail adapter can attach correlation metadata. There is no public or provider
API breaking change.

## Migration Notes

Migration `2026_09_06_000001_add_mailgun_delivery_feedback` adds four nullable
feedback timestamps to delivery records and creates the minimal, replay-safe
Mailgun receipt table. Existing deliveries remain valid and require no backfill.

The migration is additive. Application rollback may leave the unused columns
and table in place; do not run the down migration during routine rollback because
it destroys received operational evidence.

## Known Issues

- Feedback begins only after Mailgun webhooks are configured and the independent
  endpoint gate is enabled; historic delivery outcomes are not imported.
- Mailgun acceptance and final delivery are distinct. A `sent` status means the
  configured mail transport accepted the message, not that the inbox received it.
- Retention and automated pruning of webhook receipts still require an approved
  operational retention period.

## Deployment Notes

1. Back up the database and apply the additive migration.
2. Deploy web, scheduler and invitation worker from the same revision.
3. Keep all invitation issuing and the Mailgun webhook gate disabled.
4. Add the HTTP webhook signing key to the web runtime without exposing it to
   logs or source control.
5. Configure Mailgun delivered, failed and complained webhook URLs.
6. Enable only `ENCORE_MAILGUN_WEBHOOKS_ENABLED` and verify signature rejection,
   one controlled delivery and idempotent replay.
7. Confirm no recipient address appears in Mailgun receipts or audit records.
8. Invitation issuing remains subject to its existing, separate activation gate.

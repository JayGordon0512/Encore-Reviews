# v0.3.0 Enterprise Foundation

Encore exists to orchestrate the live entertainment ecosystem through trusted experiences and collective intelligence.

This document contributes to that purpose.

- Release classification: Architectural baseline
- Programme status: Complete
- Baseline effective date: 16 July 2026
- Owner: Encore Reviews Engineering
- Source branch at closure: `feature/enterprise-foundation`

## Executive Summary

Encore Reviews v0.3.0 formally closes the Enterprise Foundation Programme and establishes the permanent architectural baseline for future platform development.

The programme transformed the repository from an early application foundation into a governed Laravel platform with an Organisation-rooted domain, documented architecture, controlled provider ingestion, tenant authorization, privileged audit evidence, PostgreSQL verification, dependency security gates, and an enterprise engineering handbook.

v0.3.0 is a baseline designation, not a claim of production operational readiness. Future capabilities must conform to this architecture and pass the review gates defined in the handbook.

## Programme Objectives

The Enterprise Foundation Programme set out to:

- establish provider-neutral domain language with Organisation as the ownership root;
- define and record consequential architecture decisions;
- separate current capabilities from future direction;
- secure and make provider delivery idempotent;
- enforce tenant authorization consistently;
- make privileged administrative activity attributable;
- validate application and migrations against PostgreSQL;
- remove known dependency advisories;
- create permanent API, operational, contribution, and integration governance;
- establish a stable baseline for capability-led delivery.

These foundation objectives are complete. Product capability expansion and remaining production operations belong to subsequent programmes.

## Architecture Summary

Encore Reviews is a Laravel 12 modular monolith serving Blade web experiences, session-authenticated administration, and JSON APIs from one application and relational database.

The domain ownership chain is:

```text
Organisation
├── Users
├── Shows
│   └── Performances
│       ├── Review Invitations
│       └── Reviews
└── Venues
```

Review ownership is derived through `Review → Performance → Show → Organisation`. Provider names remain at integration boundaries and do not define core ownership.

PostgreSQL is the authoritative database, domain records use UUID identifiers except the existing numeric Laravel user key, and transactional constraints provide the concurrency authority for invitation consumption, provider identities, provider deliveries, and Organisation-scoped venues.

The service layer is an accepted direction under incremental adoption. Performance synchronization and audit recording use dedicated services; some existing workflows remain controller-led and are documented technical debt.

ADR-007 event-driven processing and ADR-008 queue-first background processing remain Proposed. The Provider Event Store is delivery-control infrastructure, not a domain event stream or queue implementation.

## Security Summary

Implemented baseline controls include:

- Laravel session authentication and CSRF protection for administrative web mutations;
- active-user and active-Organisation enforcement;
- super-administrator and Organisation-administrator separation;
- policy-led tenant authorization with explicit scoped queries;
- read-only Encore support access;
- constant-time comparison for provider credentials, signatures, and invitation-email proof;
- signed provider payloads and ±300-second freshness tolerance;
- database-backed replay protection and conflicting-payload rejection;
- encrypted original provider responses for bounded replay;
- hashed invitation tokens and normalized reviewer/invitation emails;
- append-only application-level audit records for implemented privileged actions;
- defensive exclusion of passwords, secrets, tokens, authorization data, and cookies from audit snapshots.

The baseline does not include per-Organisation provider credentials, MFA, SSO, database row-level security, provider rate limits, external tamper-evident audit storage, or a complete production secret-rotation system.

## Known Limitations

- The provider API is currently unversioned and TicketPal-specific at the route/header boundary.
- TicketPal uses one application-wide shared secret without key IDs or overlapping rotation.
- Provider-neutral v2 routes, inbound provider correlation IDs, Performance Completed, and Ticket Scanned are not implemented.
- Show synchronization and invitation creation remain controller-led.
- Provider and public endpoints lack purpose-specific rate limiting.
- Administrative identity lacks MFA, password reset, email-verification enforcement, and SSO.
- Reviewer email hashes are unkeyed and vulnerable to dictionary enumeration.
- No PHP static analyzer or JavaScript test suite is configured.
- Audit and provider-event tables have no automated retention or archival process.
- Queue and domain-event architectures remain proposed rather than operational.

## Remaining Operational Risks

### High

- One TicketPal credential has platform-wide provider-write impact and lacks scoped revocation/rotation.
- Production backup, restore, recovery objectives, and disaster-recovery ownership are not proven.
- TicketPal signed-header enforcement is a breaking integration change requiring coordinated rollout.

### Medium

- Replay responses can contain raw invitation tokens encrypted under `APP_KEY`; key protection and rotation are critical.
- No application-level provider throttling, payload quota, or abuse-monitoring programme exists.
- `integration_events` and `audit_logs` can grow without retention enforcement.
- Audit immutability can be bypassed by direct database access without least-privilege roles or external evidence storage.
- Centralized metrics, tracing, error tracking, correlation-aware logging, and alerting are not configured.
- Production deployment, rollback, backup, and incident-response procedures are not automated or exercised end to end.

No unresolved Critical repository finding was recorded at programme closure.

## Outstanding Decisions

The following decisions remain outside the Enterprise Foundation baseline:

- acceptance or supersession of ADR-007 Event-Driven Processing;
- acceptance or supersession of ADR-008 Queue-First Background Processing;
- Provider API v2 URI and credential model;
- provider scope, key identifiers, revocation, and rotation;
- authoritative inbound correlation-ID semantics;
- separation of provider delivery ID from stable provider show identity;
- provider authority to assign Organisations;
- standard provider error envelope, rate limits, and payload limits;
- Performance Completed state ownership and contract;
- Ticket Scanned ownership, privacy, retention, correction, and contract;
- production hosting, observability, backup, recovery, and service objectives;
- administrative MFA/identity roadmap;
- operational retention for audit and provider-event evidence.

Each requires the review path appropriate to its effect on domain, security, integration, deployment, tenancy, or public API.

## Recommendation

Adopt **v0.3.0 Enterprise Foundation as the official architectural baseline for all future Encore Reviews development**.

Close the Enterprise Foundation Programme and begin the next programme only through capability-level planning. The immediate engineering programme should be Enterprise Integration Readiness: coordinate TicketPal signed-request adoption, close the required provider-contract decisions, and prove the integration operationally before expanding product capability.

This recommendation does not waive the remaining production risks. Merge or release coordination must preserve the TicketPal breaking-change gate and the architecture-review requirements in the Engineering Handbook.

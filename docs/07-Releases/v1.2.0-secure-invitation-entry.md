# Encore v1.2.0 — Secure Invitation Entry

Encore exists to orchestrate the live entertainment ecosystem through trusted experiences and collective intelligence.

- Status: Implemented; activation remains prohibited pending mail and worker verification
- Date: 30 August 2026
- Governing decision: ADR-017 (Proposed)

## Release Notes

New Encore invitation emails no longer put their bearer capability in an HTTP
request URL. The email link carries the token in a browser fragment, exchanges
it through a rate-limited POST and binds the valid invitation to a rotated
server session before the review form is shown.

## Architecture Changes

ADR-017 has an implementation note for the fragment/POST/session exchange. The
ADR remains Proposed and invitation issuing remains disabled.

The review-creation transaction is shared by session-bound web submission and
the bounded legacy token-body API so single-use, email matching, review locking
and moderation defaults remain consistent.

## Operational Changes

- `/review/invitation` is the only entry URL emitted by new invitation mail.
- `/review/invitation/exchange` accepts the raw token only in a POST body,
  applies a public rate limit and rotates the session on success.
- `/review/submit` contains and submits no plaintext invitation token.
- Request-body logging is prohibited for the exchange endpoint.

## Breaking Changes

Previously issued query-string links are not accepted by the web review form.
Invitation issuing was disabled before this change, so no approved Release 1
mail journey depends on that format. The legacy `/api/reviews` token-body
contract is retained during its bounded compatibility window.

## Migration Notes

No database migration is required. Existing valid invitation records remain
redeemable through the secure exchange when their plaintext token is delivered
in the new fragment format.

## Known Issues

Invitation issuing still requires a supervised scheduler, queue worker,
verified Encore mail sender, separately rotatable mail credentials, monitoring
and controlled staging delivery evidence.

## Deployment Notes

Deploy the application normally, confirm sessions are durable, and verify that:

1. the email URL contains `#token=` and no query string;
2. the initial HTTP request target is `/review/invitation` without the token;
3. successful exchange redirects to `/review/submit`;
4. the form HTML and submission payload contain no token;
5. expired, revoked, used and unknown tokens receive one safe error category;
6. one invitation creates at most one review.

Rollback to v1.1.0 restores query-string links and therefore reintroduces the
recorded access-log exposure risk. Keep issuing disabled if rollback is needed.

## Verification

Feature coverage exercises fragment-only mail URLs, session exchange, session
rotation behavior, unavailable-token handling, session-bound submission,
single-use consumption and legacy API compatibility.
